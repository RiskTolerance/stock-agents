# Multi-Agent LLM-Based Paper Trading System Design

**Overview:**
We propose a multi-agent system for paper trading in the U.S. stock market, orchestrated using the Mastra framework. Mastra provides a TypeScript-based workflow engine to coordinate multiple AI agents with memory and tool usage in a deterministic sequence. The system mimics a real trading firm by employing specialized agents (some powered by LLMs, others by traditional scripts) that collaborate through a shared vector database memory. This memory store enables agents to persist and retrieve context (e.g. prior analyses or relevant market data) for use by others. The design emphasizes cost-efficiency by assigning heavy LLM tasks only to critical decision-making steps, while lighter models or rule-based agents handle routine analyses. By combining diverse expert agents and aggregating their judgments, the system aims to produce more informed and robust trading decisions than any single model.

## Specialist Agents and Their Roles

A **round-robin workflow** (sequential loop) orchestrates the agents, each with unique responsibilities and tools. They share information only via the memory store (a vector database) and do not directly share tools. Below is a brainstormed roster of specialist agents and their tooling/model needs:

* **Fundamental Analysis Agent:** An LLM-based analyst that evaluates company fundamentals (financial statements, earnings, valuations). It can fetch company financial data (e.g. via an API or database of SEC filings) and summarize key metrics. Tools: a financial data API function and access to a vector DB of historical fundamentals. Model: a finance-specialized LLM (possibly fine-tuned on annual reports) to interpret financial reports. This mirrors a human fundamental analyst examining intrinsic value.

* **Sentiment Analysis Agent:** A lightweight language model or script focused on market sentiment. It scrapes or receives recent news headlines, social media posts, and analyst opinions about the target stock. Tools: news API, social media sentiment feed, and possibly a pre-trained sentiment classifier (e.g. FinBERT). Model: could use an LLM (like an instruct-tuned model) to gauge tone or a simpler NLP model for sentiment scores. This agent tracks the market mood and short-term sentiment drivers.

* **News Analysis Agent:** An LLM agent specializing in news and macro events. It parses relevant news articles, economic indicators, or press releases that might impact the stock or overall market. Tools: RSS news feed or economic calendar APIs, plus the vector store for recent news context. Model: a summarization-capable LLM (for example, GPT-3.5) to produce concise summaries of news and assess its significance. By focusing on breaking news and macro data, this agent ensures that significant events are factored into decisions.

* **Technical Analysis Agent:** A rule-based or traditional ML agent handling price pattern analysis. Rather than an LLM, this agent uses time-series data and technical indicator libraries to detect trends or signals (e.g. moving average crosses, RSI overbought/oversold). Tools: a historical price database and technical indicator computation library. Model: no large LLM needed – this could be a Python script or lightweight model that outputs technical signals and possibly a recommended action (buy/sell/hold) based on technical rules. This agent emulates a technical analyst studying price charts.


* **Bullish Research Agent:** An LLM-based researcher that takes all available analyses (from fundamental, sentiment, news, technical agents via the memory store) and argues the **bull case** – i.e. why the stock should be bought or is poised to rise. It retrieves supportive evidence from the shared context (e.g. strong earnings, positive news) and forms a coherent pro-investment argument. Tools: vector DB queries (to pull relevant facts from other agents' outputs) and perhaps a knowledge base of historical bull cases. Model: a reasoning LLM (like GPT-4 or Claude) prompted to adopt an optimistic perspective. This agent is inspired by the “bull” analyst role noted in multi-agent trading frameworks.

* **Bearish Research Agent:** An LLM researcher tasked with the **bear case** – why one should be cautious or consider selling. It similarly pulls data from memory (e.g. negative news, high valuation concerns, technical weaknesses) to argue against the stock. Tools: vector DB access for contrary evidence and possibly a risk database (e.g. high debt levels, poor forecasts). Model: an LLM (comparable to the Bullish agent’s model) instructed to take a skeptical, risk-focused viewpoint. Together, the bullish and bearish agents engage in an internal “debate,” ensuring that both positive and negative aspects are analyzed for a balanced perspective.

* **Risk Management Agent:** A non-LLM agent that monitors and evaluates risk metrics of the proposed trade. It calculates factors like volatility, downside risk, position sizing relative to the portfolio, and checks compliance with risk limits. Tools: access to current portfolio exposure data, volatility indicators, and risk models (e.g. VaR calculation). This agent could be a Python script or rule engine that flags if the aggregated decision would exceed risk thresholds (for instance, if multiple agents vote “buy” but the position would overly concentrate the portfolio). It may adjust the confidence of a trade or suggest a hedge. By design, it functions like a human risk manager overseeing the traders. 

* **Trader/Decision Agent (Coordinator):** This is a high-level LLM agent or orchestrator module that synthesizes all inputs and ultimately decides the action *Buy, Sell,* or *Hold*. In practice, this role can be split into multiple trader agents with different risk profiles (e.g. an aggressive trader agent vs. a conservative one) that each make a recommendation. For simplicity, we consider a single coordinator agent here (akin to a fund manager). Tools: it primarily interacts with the memory store to read each agent’s conclusions (fundamental outlook, sentiment score, bull/bear arguments, risk flags, etc.). Model: a powerful LLM (e.g. GPT-4 or a large open-source model) for deep reasoning on all gathered evidence. This agent applies a predetermined decision logic or prompt to weigh each perspective and produce a final trading decision. It may also have a tool to execute the paper trade in the simulation environment (or simply log the action). The coordinator ensures all agents’ contributions are considered and that the final decision adheres to risk constraints (it may adjust or override recommendations if the Risk agent indicates unacceptable risk). In essence, it **aggregates the “votes” of the other agents and issues the final buy/sell/hold decision**.

Each agent above has distinct tools and expertise, reflecting a division of labor much like a real trading team. The Mastra workflow engine would call these agents in sequence (e.g. collect data -> run analysts -> run bull/bear researchers -> run risk check -> finalize decision), passing along the shared context. All intermediate outputs (analyses, summaries, signals) are stored in the vector database or a structured shared memory, acting as a **persistent blackboard** that the later agents query for relevant details. This structured communication ensures that information is not lost across agents – an approach akin to using structured reports instead of a pure free-form “telephone game” dialogue.

## Voting Scheme and Agent Weighting

To turn the agents’ insights into a trading action, the system employs a weighted voting ensemble of the agents’ recommendations. After all agents have contributed their analysis, each **agent effectively casts a vote**: Buy (+1), Sell (–1), or Hold (0). Rather than treating all votes equally, the system weights each agent’s vote based on factors such as relevance, confidence, and historical accuracy:

* **Domain Relevance:** The importance of each agent’s expertise can vary with context. For example, if a major earnings report just dropped or significant fundamental news came out, the **Fundamental Analysis** agent’s insights gain relevance and could be given higher weight for that decision. Conversely, during market panic or euphoria, the **Sentiment** agent’s vote might be weighted more heavily as sentiment dominates price action. The system can dynamically adjust weights based on scenario triggers (news events, volatility spikes, technical regime, etc.), ensuring the most pertinent agent has a stronger influence when appropriate. This context-aware weighting echoes the idea of selecting the right expert for each situation.

* **Confidence Scores:** Each agent’s output can include a self-reported confidence level or a probability for its recommendation. The voting scheme uses these confidence scores as weights—agents that express high certainty in their Buy/Sell call will have their vote magnified proportionally. For instance, if the Technical agent gives a strong buy signal with high confidence (e.g. multiple indicators aligning), that vote counts more than a weakly confident buy. This mechanism is analogous to ensemble methods that use confidence or probability outputs to weight model votes. By integrating confidence-weighted voting, the ensemble leverages not just the direction of each agent’s advice but also the strength of conviction behind it.

* **Historical Reliability:** Over time, the system can track each agent’s performance (did their past recommendations lead to profitable or accurate outcomes?). Agents that have a strong track record (e.g. the sentiment agent correctly anticipated many moves) are assigned higher base weights, whereas consistently underperforming agents are down-weighted. This can be implemented via a dynamic weighted-majority algorithm, where weights are updated based on recent prediction accuracy or profit contribution. For example, if the Fundamental agent’s calls have been especially reliable in the last quarter, the system will trust it more in the vote aggregation. These weights can continuously evolve (e.g. using an exponentially weighted moving average of past successes) so the ensemble adapts to which agent is currently most effective.

Using these factors, the **final decision rule** might work as follows: sum up all weighted votes and examine the total. If the weighted sum is strongly positive, the consensus is a **Buy**; strongly negative suggests a **Sell**; if near zero, the agents are divided or favor caution, yielding a **Hold** or no-action decision. In practice, the coordinator (Trader agent) can implement this calculation, or it can qualitatively incorporate the factors in an LLM prompt (e.g., *"Given each specialist's recommendation and confidence, decide the best action."*). This weighted voting approach is supported by research showing that ensembles of models/agents outperform individuals in trading tasks, improving returns and risk metrics by combining strengths. The voting process thus integrates diverse viewpoints into a single action, with a bias toward those agents most likely to be correct in the current context.

## Training and Tuning Strategies

Designing and tuning this multi-agent system requires careful consideration to ensure cost-effectiveness, coherent memory sharing, and strong performance. Below are proposed strategies for training and optimizing the agents and their collaboration:

* **Specialized Agent Training:** Each LLM agent should be tuned or prompted for its specific domain. Rather than using a large generic model for all tasks, we can fine-tune smaller models on domain-specific data. For example, the Fundamental agent could be fine-tuned on financial reports and Q\&A transcripts to better interpret financial metrics, while the News/Sentiment agent might be fine-tuned on financial news articles to improve its grasp of market context. If fine-tuning full models is costly, few-shot prompting or instruct tuning can be used to shape a pre-trained model’s style (e.g. giving the fundamental agent exemplars of analyzing balance sheets). Training data can include historical cases: past market scenarios with known outcomes, so that agents learn patterns (e.g. how sentiment surges often reverse, or how certain technical patterns predict moves). Non-LLM agents (Technical, Risk) can be developed using traditional supervised learning on historical price data or simply by encoding well-known formulas and rules. Ensuring each agent is *really good at its niche task* will improve the quality of the information in the system.

* **Memory and Context Sharing:** A vector database (like Couchbase or other vector stores) is central to enabling agents to share knowledge without prompt length explosion. We will need to preprocess and embed the outputs of early agents (e.g. embedding the fundamental summary, sentiment summary, etc.) and store them with appropriate metadata (e.g. which stock, date, agent source). Later agents’ prompts will include a step to query this vector store for relevant information. For instance, the Bullish/Bearish Research agents can perform similarity search to retrieve the fundamental and news summaries about the stock before forming arguments. Training the system involves refining what each agent stores (perhaps using a schema or structured report format for consistency) and how they retrieve. We might develop prompt templates that explicitly cite the memory (“According to the Fundamental Analysis: *< data >* ...”). During tuning, we can evaluate whether agents are correctly picking up each other’s signals from memory. If an agent tends to ignore important context, we might adjust its instructions to pay more attention to memory results (e.g. **prompt chaining** with retrieved context). The memory also serves as long-term context across trading days – agents can recall what they concluded in previous rounds about the same stock (simulating memory of prior reasoning).

* **Cost Optimization Techniques:** To keep the system cost-effective, we leverage **model cascades and tool heterogeneity**. Simpler or cheaper models handle the initial or frequent tasks, while expensive LLM calls are minimized. For example, the Technical and Risk agents use deterministic logic or small models (no cost per use), the Sentiment agent could use an open-source model or API with low cost, and only the final Trader agent (or possibly bull/bear debaters) use a top-tier LLM like GPT-4. We can implement an **LLM cascade**: try using an open-source LLM for the coordinator’s reasoning, and only if its confidence is low or if a particularly complex scenario arises do we invoke a larger LLM (“ask the expert” strategy). This approach was shown to drastically cut costs while even improving success by reserving GPT-4 for crucial moments. Additionally, we can reduce token usage by using the vector store to pass info instead of stuffing entire analyses into each prompt. The Mastra framework’s deterministic workflow helps us avoid unnecessary recomputation – each agent only runs when needed and passes its results onward. Monitoring tools can log each agent’s runtime and API calls so we can identify bottlenecks and optimize (for instance, if the News agent’s LLM call is rarely adding value, we could replace it with a summary from a news API to save tokens).

* **Ensemble Weight Tuning and Feedback:** The weighting scheme for votes can itself be tuned using historical data. We might initialize agent weights based on expert judgment (e.g. give fundamental and technical 30% each, sentiment 20%, bull/bear 10% each, etc.) and then adjust through backtesting. By running the multi-agent system on past market periods (paper trading on historical data), we can evaluate performance (returns, Sharpe ratio, drawdowns) and use algorithms to optimize the weights. One approach is **reinforcement learning** or evolutionary strategies to find weight settings that maximize a reward (like profit minus risk penalty) over many simulated trades. Alternatively, the system can update weights online: e.g. using a form of Weighted Majority Algorithm, increase an agent’s weight if its calls were right and decrease if wrong. This kind of dynamic ensemble learning has proven effective in trading contexts to improve accuracy and profitability over static models. We will also tune the confidence calibration – ensuring that an agent’s reported confidence correlates with actual success probability, so the weighting by confidence is meaningful. This may involve calibrating output probabilities from LLMs or using reliability metrics from validation data.

* **Performance and Trade-off Considerations:** We must balance the depth of analysis with the speed required for trading. Paper trading on daily data allows a reasonable time budget for analysis each day, but intraday trading would demand faster decisions. We can parallelize some agents where possible (e.g. fundamental and sentiment analysis could run concurrently on separate threads, since Mastra supports asynchronous workflows). However, since later agents depend on earlier ones’ outputs, the critical path is sequential. During development, we’ll profile the end-to-end latency and trim any unnecessary overhead. Caching can be applied — for example, if the same stock’s fundamentals don’t change daily, the Fundamental agent’s output can be cached for reuse unless new earnings arrive. Another trade-off is complexity vs. maintainability: we propose \~8 agents, which is manageable, but adding too many could make the system harder to tune or explain. We will monitor for “analysis paralysis” (agents providing redundant or conflicting info). If an agent isn’t contributing unique value, we might remove or merge it to streamline the team. Conversely, if we find a gap (say, no agent analyzing macroeconomic regime), we could introduce another specialist.

By following these training and tuning strategies, we can iteratively improve the multi-agent trading system. We will start simple – ensure each agent works correctly in isolation, then in pairs, and gradually build up to the full orchestration. Throughout, we’ll use **evaluation metrics** (e.g. paper trading return vs. S\&P500, Sharpe ratio, drawdown) to guide adjustments. The result is a cost-aware, collaborative ensemble of LLM and non-LLM agents that leverage shared memory to make well-rounded trading decisions. This design not only aims for better performance than single-agent approaches, but also provides transparency: each agent’s rationale (stored in memory) can be reviewed, and the weighted vote can be understood as a form of explanation for the final action – an important feature when building trust in AI-driven trading systems.
